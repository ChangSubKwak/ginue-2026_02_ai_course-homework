# 바이브코딩 개발 과정 요약 (문서 작성 근거 자료)

## 사용 도구
- AI 코딩 에이전트: Claude Code(Anthropic). 개발자는 자연어 지시(프롬프트)로 요구사항·제약·검증 기준을 주고, AI가 설계·구현·테스트·문서 초안을 수행. 개발자는 결과를 검토하고 방향을 결정.
- 실행 환경: Windows 10 PC, 브라우저 Chrome/Edge. 빌드 도구·서버 없음(순수 HTML/CSS/JS).
- 자동 검증 도구(AI가 작성): 정적 점검 스크립트(lint-app.js: alert/모듈/외부 리소스/테마 토큰 규약 위반 탐지), 스모크 점검(pw-check.js: Playwright+Edge로 콘솔 오류·페이지 예외·가로 스크롤·3개 뷰 스크린샷), 인터랙티브 테스트 러너(pw-run.js: 수용 기준을 클릭·입력으로 검증, 스크린샷 촬영).
- 형상 관리: Git, GitHub 공개 저장소(ChangSubKwak/ginue-2026_02_ai_course-homework), GitHub Pages로 온라인 실행.

## 절차 (실제 수행 순서)
1. 과제 요구사항 정리: 5개 카테고리(교과 교육지원·학습지도·학교 업무 자동화·학교 행정 지원·교육용 게임)에 앱 1개씩, 제출물은 개요·설명서 문서 + 소스 zip + 실행 페이지.
2. 기술 제약 결정(개발자 판단): 순수 클라이언트(HTML/CSS/JS), 외부 라이브러리·서버·API 키 없음, index.html 더블클릭 실행, localStorage 저장 + JSON/CSV 입출력, 한국어 UI, 반응형, 가상 샘플 데이터 내장. 이유: 학교 PC·태블릿·전자칠판에서 설치 없이 열리고, 심사자가 바로 실행할 수 있어야 함.
3. 컨셉 제안(AI, 멀티 에이전트): 카테고리마다 3개 관점(현장 교사 실용성 / 학습 효과·학생 참여 / 기술 완성도·시연 임팩트)의 에이전트가 각 2개 컨셉을 제안 → 총 30개 컨셉.
4. 심사·스펙 확정(AI): 카테고리별 심사 에이전트가 교육적 가치(25)·현장 실용성(25)·구현 가능성(20)·차별성(20)·카테고리 적합성(10) 기준으로 1개를 선정(필요 시 두 안을 합침)하고 구현 스펙(기능 우선순위 must/should/nice, 화면, 데이터 모델, 알고리즘, 샘플 데이터, 엣지 케이스, 수용 기준 13~20개)을 작성. 이어서 정합성 검토 에이전트가 5개 스펙의 카테고리 경계 중복, 기술 다양성(앱마다 다른 대표 기술), 이름 톤, 공통 샘플 데이터(가온초등학교 5학년 2반, 담임 이가람, 학생 24명), 시각 아이덴티티(액센트 색·서체)를 통일.
5. 공통 구현 규약 작성(AI 초안, 개발자 확정): 파일 구조, file:// 실행 보장(ES 모듈·fetch 금지), 테마 토큰 3블록(라이트/다크), safe-area 패딩·400px 반응형, localStorage try/catch 래퍼, alert/confirm/prompt 금지(인앱 모달·토스트), 접근성(focus-visible, aria, reduced-motion), README 템플릿, 자가 점검 체크리스트.
6. 구현(AI, 앱당 빌더 에이전트 1명): 스펙+규약을 읽고 앱 전체를 작성한 뒤 lint·스모크·수용 기준 자가 점검, README 작성, 테스트용 window.__app API 노출. 앱당 코드 1,400~2,340줄.
7. 3관점 검증(AI, 앱당 3명 병렬, 소스 수정 금지): ① 기능 테스트(독립 작성한 Playwright 모듈로 수용 기준·공통 시나리오 실행) ② 코드 리뷰(논리·상태/렌더·데이터·XSS·규약·스펙 누락) ③ UX·시각 리뷰(데스크톱·태블릿·모바일·다크·인쇄 스크린샷 수십~수백 장을 보고 판단). 결함은 critical/major/minor로 기록.
8. 수정·재검증 루프(AI): 수정 에이전트가 결함을 고치고 기존 테스트를 전부 재실행 → 독립 재검증 에이전트가 수정 주장을 믿지 않고 직접 확인(회귀 탐지) → critical/major 0건이면 종료, 아니면 다음 라운드(최대 3라운드).
9. 문서화·패키징: 앱별 개요·설명서(docx/pdf), 전체 과제 보고서, 소스 zip, GitHub 저장소·Pages 배포.

## 실제 사용한 프롬프트 요지 (요약)
- 초기 지시: "바이브코딩으로 만드는 교육용 앱 개발 — 교과 교육지원·학습지도·학교 업무 자동화·학교 행정 지원·교육용 게임 5개 앱을 폴더별로 개발. 과제 제출물로 개요·설명서 문서, 소스 압축, 구현 사이트 포함."
- 컨셉 제안: "당신은 15년 경력 초등 담임교사(또는 교육공학 연구자 / 시니어 프론트엔드 개발자)입니다. 카테고리 N에 맞는 앱 컨셉 2개를 제안하되 기술 제약 안에서, 한국 초등 현장의 용어·절차를 반영해…"
- 심사·스펙: "6개 컨셉을 100점 기준으로 심사해 1개를 확정하고, 개발자가 추가 질문 없이 구현할 수 있도록 features(must≤8)/screens/data_model/algorithms/sample_data/edge_cases/acceptance_criteria(테스트 가능한 문장)를 작성…"
- 구현: "공통 규약을 먼저 읽고 규약을 스펙보다 우선. must 전부 구현, 샘플 데이터 내장, alert 금지, 라이트/다크 모두 디자인, 완료 전 lint 0건·스모크 0건·수용 기준 확인, README 템플릿 채우기…"
- 검증: "목표는 결함을 찾는 것(통과시키는 것이 아님). 빌더의 테스트를 믿지 말고 독립 모듈을 작성. 입력 검증·XSS 문자열·새로고침 복원·가져오기 오류·400px·다크 모드까지…"
- 수정: "critical·major는 반드시 수정, 지적이 틀렸다고 판단되면 재현해 근거를 적고 not_fixed로. 기존 테스트 모듈 전부 재실행. 새 기능 추가 금지."
- 재검증: "수정 보고서의 주장을 그대로 믿지 말고 소스·브라우저로 직접 확인. 회귀 탐지. critical/major 잔여 0이면 pass."

## 배운 점 (문서 8.3절 근거)
- 제약과 수용 기준을 문장으로 명확히 주면 AI 산출물의 편차가 크게 줄었다(예: "file://에서 동작" → ES 모듈/fetch 금지로 구체화).
- 만든 사람과 검증하는 사람을 분리하면 빌더의 자가 점검이 놓친 결함(예: 교사용 자리표 180° 회전 시 격자 붕괴, 가져오기 JSON 깊은 검증 부재, 가져온 문자열의 XSS)이 드러났다. 빌더의 "수용 기준 전부 통과" 보고는 DOM 순서만 확인한 경우가 있었다.
- UX 리뷰는 스크린샷을 실제로 보게 해야 의미가 있었다(글자 크기 6~9px, 대비 2.2:1, 모바일 메뉴 잘림 등은 코드만 봐서는 발견되지 않음).
- 세션 중단(사용량 제한)이 잦아, 모든 중간 결과를 파일(JSON·스크린샷)로 남기고 git에 커밋하는 습관이 재개 비용을 줄였다.
- 교육 현장 맥락(생활기록부·특별실·학사일정·전자칠판 시연)은 프롬프트에 명시해야 반영되었다.
